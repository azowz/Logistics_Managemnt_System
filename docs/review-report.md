# تقرير مراجعة وتنظيف Mesaar

تاريخ الإكمال والتحقق: 2026-10-18. نقطة البداية: `c5eeae2976f2b99efcbbde3ca447d3d49da1fe16`.
يشمل الحصر الملفات المتتبعة والملفات غير المتتبعة الموجودة عند بدء المهمة، ويستثني البيئة
الافتراضية وملفات Cache و`node_modules` والأسرار المحلية.

## 1. المعمارية

حُفظت بنية `app/` وحدود المجالات: Routes ثم Services ثم Repositories/Models، مع مسار
مستقل للأحداث والإسقاطات والعمّال. لم تُنقل وحدات تشغيلية دون حاجة، ولم تُدمج مسؤوليات
Order وShipment وEquipment وCompliance وBilling.

- أصبحت عملية استهلاك تسوية المطالبة وتعديل الفاتورة وإصدار الأحداث معاملة واحدة؛ فُصل
  تحضير التسوية الخاص عن واجهتها العامة التي تحفظ المعاملة.
- جُمعت أربع دوال متطابقة لمعالجة الوقت عند القراءة في `app/common/datetime.py::ensure_aware`.
  تظل كتابة التواريخ خاضعة لتحقق المخططات، ولا تُقبل التواريخ دون منطقة زمنية تلقائيًا على API.
- فُصلت اعتماديات التطوير في `requirements-dev.txt`، ووُحّدت إعدادات الجودة في
  `pyproject.toml` وMakefile وCI. أصبح فحص Mypy مطلوبًا في CI بعد إصلاح أخطائه.
- يستخدم API وWorker وBeat في Compose دور `mesaar_app` غير القادر على تجاوز RLS.
  دور `mesaar` الإداري يبقى لتهيئة PostgreSQL فقط. تعليمات ترقية المجلدات القائمة في
  [التشغيل](operations.md).

لم يُعدَّل أي ملف من سلسلة الترحيلات التاريخية، ولم يتطلب العمل Migration جديدة.

## 2. إصلاحات الكود المثبتة

| المشكلة قبل الإصلاح | السلوك بعد الإصلاح |
| --- | --- |
| JWT قديم بلا `tid` يستطيع إبقاء نطاق طلب العميل/المنصة | يُستنتج المستأجر من المستخدم المحفوظ وتُضيَّق GUC في المعاملة الحالية؛ Header العميل لا يثبت هويته |
| عدم رفض المستخدم المحذوف منطقيًا في بعض مسارات المصادقة | رفضه في JWT وLogin وRefresh، مع رفض عدم تطابق `tid` مع مستأجر المستخدم |
| فشل تطبيق GUC يُبتلع على PostgreSQL | ينتشر الخطأ فتتوقف العملية؛ تظل SQLite بلا GUC |
| إنشاء Order قد يقبل Customer من مستأجر آخر خارج حماية RLS | تحقق صريح من ملكية العميل للمستأجر |
| تعارض Outbox داخل SAVEPOINT يلغي آثار handlers السابقة | يتولى SAVEPOINT تراجع المعالج الفاشل وحده؛ يُحفظ سلوك rollback خارج المعاملة المتداخلة |
| `delivered_at` لا يُحفظ عند تسليم الشحنة | يُضبط قبل حدث `ShipmentDelivered` |
| التسوية قد تُحفظ قبل رفض تعديل الفاتورة | التسوية والفاتورة والأحداث تُحفظ أو تتراجع معًا |
| تحديث مبلغ التسوية يتجاوز حد المطالبة المعتمد | إعادة تطبيق قاعدة المبلغ عند التعديل |
| تعديل الحمولة يتجاوز السعة/قيود المعدات | فحص المخازن والمعدات بالحمولة المقترحة، مع استبعاد حجز الشحنة نفسها |
| إمكان إسناد الشحنة لحساب سائق معطل/محذوف | رفض الحساب أو ملف السائق غير المؤهل، وفحص المستأجر في قبول السائق |
| UUID في Tracking يفشل في الحفظ أو الاستجابة | تحويل الإدخال الداخلي إلى UUID والاستجابة إلى strings مع بقاء عقد API |
| الحدث الثاني للتتبع يفشل عند مقارنة توقيت SQLite | مقارنة واعية بالمناطق الزمنية، ورفض الحدث الأقدم |
| مسارات 404 العشوائية تنشئ تسميات Prometheus غير محدودة | تسمية واحدة `unmatched` لكل المسارات غير المطابقة |
| سجل جاهزية Worker يتضمن URLs قد تحمل كلمات مرور | حذف URLs من سجل التطبيق المخصص |

صُححت أيضًا تواقيع المستودعات وProtocol الأحداث ونتائج القيم الاختيارية واستيرادات
النماذج المفقودة في Type Hints، دون تغيير عقود الأحداث.

حُدث `python-jose` من 3.3.0 إلى 3.5.0 و`python-multipart` من 0.0.9 إلى 0.0.32، ثم
أُعيدت الاختبارات. يسجل مشروع jose إصلاحات CVE-2024-33663/33664 في 3.4.0، وإزالة
بيانات مفاتيح حساسة من بعض الأخطاء في 3.5.0؛ راجع [سجل المشروع](https://github.com/mpdavis/python-jose/blob/master/CHANGELOG.md).
ويحدد إشعار multipart إصلاح استهلاك CPU في 0.0.30؛ راجع [إشعار المطور](https://github.com/Kludex/python-multipart/security/advisories/GHSA-5rvq-cxj2-64vf).
هذا لا يمثل فحص CVE شاملًا لجميع الاعتماديات أو إثبات قابلية استغلال كل إشعار في التطبيق.

## 4. التوثيق

أصبح [README](../README.md) مدخل التشغيل، و[docs/README](README.md) فهرسًا للمراجع العربية
الحالية: المعمارية والمجالات والبيانات وAPI والتطوير والتشغيل والحالة والمسرد والرؤية.
حُفظت القرارات التسعة في `docs/adr/` مع أسبابها وتواريخها وفروق التنفيذ الفعلي.
تُميز وثيقة [الحالة](status.md) التنفيذ والاختبار الفعلي عن المخطط والمنفذ جزئيًا.

حُفظت أصول وثائق الأرشيف بلغتها التاريخية، وأُضيف فهرس عربي يوضح أن محتواها لا يصف
الحالة الحالية. ترجمة الأرشيف كاملًا تبقى عملًا توثيقيًا؛ لا تعني الأرشفة اعتماد تصميمه
أو تنفيذ ميزاته. لم تُحذف الأصول الهندسية المهمة لتقليل عدد الملفات.

## 5. التحقق الفعلي

بيئة التحقق: Windows وPython 3.12.10، وPostgreSQL 17 مؤقت مستقل بأدوار
`NOSUPERUSER NOBYPASSRLS`. لا تُستخدم قاعدة المستخدم المحلية لهذه الاختبارات لأنها
تنشئ الجداول وتحذفها. CI وصورة Docker يستهدفان Python 3.11 وPostgreSQL 16.

| الفحص | النتيجة |
| --- | --- |
| خط الأساس قبل تثبيت الاعتماديات | فشل جمع الاختبارات بسبب غياب `loguru` و`redis` |
| خط الأساس بعد تجهيز البيئة | 1505 ناجحًا و16 متخطى؛ المجموع 1521 |
| الاختبارات النهائية مع PostgreSQL | 1562 ناجحًا، دون تخطٍ، وتحذير PendingDeprecation واحد من استيراد multipart في Starlette القديم |
| `ruff check .` | ناجح |
| `black --check app` | ناجح؛ 168 ملفًا |
| `mypy app` | ناجح؛ 168 ملفًا، مقابل 57 خطأً في 20 ملفًا قبل العمل |
| `alembic upgrade head` ثم `alembic check` | ناجح حتى `0019`؛ لا اختلافات مخطط جديدة |
| سكربت دور PostgreSQL المحلي | نُفذ مرتين بنجاح، والدور الناتج لا يمتلك superuser أو bypassrls |
| تشغيل Uvicorn و`/health/live` | ناجح فعليًا |
| Readiness مع Redis غير متاح | 503 كما هو متوقع، مع نجاح فحص PostgreSQL |
| مقارنة OpenAPI قبل/بعد | تطابق كامل: 183 مسارًا و204 مخططات |
| `pip check` | لا اعتماديات مكسورة |
| `docker compose config --quiet` | ناجح |
| بناء Docker وتشغيل الحزمة الكاملة | لم يُنفذا: Docker daemon غير متاح |
| `npm run typecheck` في مجلد mobile الأصلي | فشل مع أخطاء React Native/types أثناء تعديلات اعتماديات متزامنة؛ لم يُدعَ نجاحه ولم تُستبدل تغييرات الجلسة الأخرى |

Black هو المنسق المعتمد في Makefile وCI. نُفذ أيضًا `ruff format --check .` بوصفه فحصًا
تشخيصيًا؛ اقترح إعادة تنسيق ملفات موجودة، بما فيها الترحيلات والاختبارات. لم يُعتمد منسق
ثانٍ ولم تُغيَّر الترحيلات التاريخية لإرضاء اختلاف تنسيقي.

## 6. الديون المتبقية

1. يحتاج تفويض CLIENT/DRIVER على الموارد داخل المستأجر إلى نموذج ملكية واضح؛ RBAC
   الحالي لا يكفي لتقييد كل مورد لصاحبه. كذلك يبقى هوية مسجل Tracking قابلة للإرسال من العميل.
2. relay وWebhook sweep لا يحجزان الصفوف؛ تظل المعالجة المتزامنة وترتيب أحداث aggregate
   المؤجلة بحاجة إلى تصميم واختبارات تنافس. إصلاح SAVEPOINT لا يحل هذه المسائل.
3. إعادة بناء الإسقاطات تحتاج تنسيق watermark مع الأحداث المعلقة وسجل المعالجة؛
   وحساب الإيراد من `PaymentRecorded` يحتاج تمييز حالة الدفعة بعقد متوافق.
4. نطاق المنصة للعمليات دون مستأجر، وفشل denylist المفتوح عند انقطاع Redis، وسياسة
   `iss`/`aud` تحتاج قرارات مصادقة مستقلة. لم تُغيّر دلالات التوكنات بصمت.
5. تبقى مراجعة SSRF عبر DNS/Egress، ومحدد معدل موزع، وKMS، وForeign Keys مركبة للمستأجر.
6. التطبيق المحمول يعتمد Mock في المسار الحالي؛ تكييف استجابات API، ومعالجة 204،
   والعد التنازلي أثناء التحميل، وتوافق حزمة Expo/React Native تحتاج تحققًا مستقلًا.
7. لا يوجد lock شامل للاعتماديات العابرة أو تدقيق ثغرات آلي شامل، ولم تُجرَّب صورة Docker.

زيادة العدد ناتجة عن ستة ملفات مفيدة جديدة مقابل حذف ملفين فارغين؛ لا توجد نسبة أداء
مزعومة أو تقليل مصطنع لعدد الملفات. كانت 11 وثيقة عربية غير متتبعة موجودة قبل المهمة؛
حُفظت وطُورت، ولا تُحسب تأليفًا جديدًا بالكامل.

أعادت جلسة أخرى المستودع الأصلي بـ`reset --hard` وعمليات تنظيف أثناء العمل. حُفظت نقطة
البداية خارج المشروع في `before.zip`، ثم استعيدت الإصلاحات في worktree
`C:/me/project/Mesaar_cleanup_review` على `audit/mesaar-cleanup`، وأُعيد التحقق منها.
أُعيدت التغييرات إلى المشروع الأصلي بعد فحص التعارضات، مع الحفاظ على تعديلات `mobile`
الأخرى وملف `.env`. أُعيد تشغيل الحزمة هناك: **1562 اختبارًا ناجحًا**، وفحوص Ruff وBlack
وMypy ناجحة، وتشغيل Uvicorn ومقارنة OpenAPI ناجحان. نُقلت 122 نسخة ملف، وأُزيلت
35 مسارًا قديمًا؛ 33 منها نُقل محتواها للأرشيف واثنان فارغان.
لا يتضمن هذا العمل Commit أو نشرًا أو تعديلًا لقاعدة المستخدم.
